# M6 打包与发布:设计草案

状态:草案,2026-11-04 起草,等维护者过目。确认之前不动 STATUS 里「update* 第二部分」和打包的任何代码。
本文是自己的设计,依据:前端 panel/src(api/openbox.ts 的 OpenboxUpdate* 类型、OpenboxUpdateCard)、
backend 现有代码(internal/system/paths.go、internal/update、internal/singbox/deploy.go)、sing-box / OpenWrt / Debian 的公开文档。
没有读取、也不参照上游的 scripts/install.sh、update.sh、uninstall.sh、release-components.py、fetch-upstream-kernel.sh、build-release.sh
(它们是上游同步来的,会被覆盖,且受上游许可约束,见 HANDOFF 第六节)。

## 一、对账时发现、会影响设计的现状

1. main 上现在没有任何工作流。backend.yml 在提交 e102f61a(「Replace with upstream」同步)里被删掉了;
   HANDOFF 说 .github/workflows 在 KEEP 里,但实际以维护者本机 sync-main.sh 为准,这两者对不上。
   后果:云端的 vet / test / 编译验证现在没有在跑。见第十二节第 1 条,需要维护者回答。
2. scripts/ 下的 install.sh、update.sh、uninstall.sh 等是上游版本(提交说明都是「Replace with upstream」),不是我们的。
   M6 的安装、卸载脚本要自己写,放进同步不会覆盖的位置(backend/packaging/)。
3. core/scripts/build.sh 默认从 panel/server/index.mjs(上游闭源产物)里读 buildID 并注入。后端不校验 buildID(DESIGN D5),
   所以 M6 不调用这个脚本:另写 backend/packaging/build-core.sh,直接 go build 核心,不注入 buildID,也不读任何上游产物。core/ 本身不改。
4. internal/update 的 check 只跳过草稿,不看发布里有没有安装包。仓库里有上游同步产生的 v0.1.396 到 v0.1.400 标签;
   一旦出现一个没有后端安装包的更大版本号,check 会报「有新版」,run 却下不到包。M6 要让 check 只认带本架构安装包的发布。
5. 默认数据目录 /var/lib/openbox-backend 在 OpenWrt 上会丢:OpenWrt 的 /var 是指向 /tmp 的链接,重启即清空。
   所以 OpenWrt 的服务脚本必须显式给 OPENBOX_DATA_DIR 和 OPENBOX_CONFIG_DIR(见第四节)。Debian 用默认值。
6. 后端已有 GET /api/health(免登录),健康检查直接用它。

## 二、目标与非目标

目标:一份发布(GitHub Release)里,每个架构(linux amd64 / arm64)一个自包含的安装包,包含后端、openbox-core、sing-box、前端、规则库;
全新安装一条命令;在线升级可回滚;任何一步失败都不能把路由器弄到不能联网。
非目标:Docker(不在范围)、签名(v1 不做,只做 SHA256 加 HTTPS)、delta 升级、降级到任意旧版、跨大版本的数据迁移。

## 三、安装包格式

每个架构一个压缩包,文件名 openbox-<版本>-linux-<架构>.tar.gz,架构写 amd64 或 arm64。版本即发布标签,如 v0.1.400-main.1。
同一次发布里另有:SHA256SUMS(所有压缩包的校验和,sha256sum 格式)、install.sh、uninstall.sh(也作为单独资产,方便 curl 下载)。

压缩包内容(顶层目录 openbox-<版本>-linux-<架构>/):
- manifest.json:见下
- bin/openbox-backend
- lib/openbox-core、lib/sing-box(放在私有目录,见第四节理由)
- share/panel/:panel/dist 的全部文件
- share/geodata/:geosite-*.srs、geoip-*.srs、geodata.json(规则库清单)
- init/:openwrt 的 procd 脚本、debian 的 systemd 单元(模板,安装时填路径)
- install.sh、uninstall.sh(与单独资产相同)

manifest.json(自己定义,格式名 open-box-release,version 1):
  format、version(发布版本号)、upstream(上游号,如 400)、arch、builtAt(RFC3339)、
  components:{backend:{version}, core:{version}, singbox:{version}, panel:{version}, geodata:{version, date}}、
  files:[{path, sha256, size, mode}](压缩包里除 manifest.json 自己外的每个文件)。
校验分两层:压缩包整体对 SHA256SUMS;解出的每个文件对 manifest.files。

geodata.json:{version, date, counts:{geosite, geoip}}。这三个值就是 GET /update/status 的 geoVersion、geoDate、geoCounts。
counts 的含义要和前端显示对一下,草案取「geosite-*.srs 和 geoip-*.srs 各有多少个分类文件」。
规则库的版本取 date(构建时从固定来源取到的日期),来源见第六节。

体积:没有实测。首次构建后把各部分大小写进 STATUS,再决定是否需要把 geodata 拆成独立资产(v1 不拆,随整包更新)。

## 四、安装位置、服务名与路径

通用:
- /usr/bin/openbox-backend:后端二进制
- /usr/lib/openbox-backend/openbox-core、/usr/lib/openbox-backend/sing-box:放私有目录,不放进 PATH。
  理由:OpenWrt 官方源有 sing-box 包、用户也可能自己装过,放 /usr/bin 会互相覆盖。服务脚本用 -sing-box、-core 参数指到私有目录。
- /usr/share/openbox-backend/panel、/usr/share/openbox-backend/geodata:与 paths.go 的默认值一致,不用改。
- 配置目录:Debian /etc/openbox-backend(默认值);OpenWrt /etc/openbox-backend(也是默认值,在 overlay 上,持久)。
- 数据目录:Debian /var/lib/openbox-backend(默认值);OpenWrt 必须改:/etc/openbox-backend/data,由 procd 脚本传 OPENBOX_DATA_DIR。
  闪存磨损:数据里有流量统计、延迟历史,写得比较勤。目标设备是 arm64 / amd64 的路由器,通常是 eMMC / SSD / SD 卡,草案接受;
  维护者若不接受,可以让 OpenWrt 的数据目录由用户在安装时指定(见第十二节第 3 条)。DNS 查询日志已经在内存盘(DESIGN 第 8 节),不受影响。
- 服务名:后端 openbox-backend(与 paths.go 默认一致)。sing-box 的服务名建议改成 openbox-singbox,
  不用 sing-box:OpenWrt 自带的 sing-box 包的 init 脚本叫 sing-box,同名会冲突。改法是改 paths.go 的 DefaultCoreService 一处,
  冲突检测已经排除自己的 sing-box 服务名(靠配置传入),不受影响。见第十二节第 2 条。

服务定义:
- OpenWrt:/etc/init.d/openbox-backend、/etc/init.d/openbox-singbox(procd,USE_PROCD=1,respawn)。
  后端的脚本带环境变量(数据目录、配置目录)和 -sing-box / -core 参数。sing-box 的脚本不自己带配置逻辑:
  配置由后端部署时写到配置目录,脚本只负责 start / stop,与现有 service 接口(running / enabled / start…)的假设一致。
- Debian:/etc/systemd/system/openbox-backend.service、openbox-singbox.service。Restart=on-failure,后端以 root 运行(要管 DNS、防火墙、网络命名空间)。
- 两个服务的开机自启由安装脚本设置;后端的开机自启只是用户可见的状态,现有 service 接口已能读。

## 五、安装、卸载脚本(自己写,放 backend/packaging/)

install.sh(POSIX sh,busybox ash 和 dash 都能跑):
1. 识别系统:/etc/openwrt_release 存在是 OpenWrt;/etc/os-release 的 ID 是 debian 或 ubuntu 系是 Debian 系;其它直接退出并说明。
2. 识别架构:uname -m 的 x86_64 对应 amd64、aarch64 对应 arm64;其它退出。
3. 取安装包:默认从本仓库最新发布下载(GitHub API,不带凭据),可用 --version 指定,可用 --mirror 前缀走镜像,可用 --file 指向本地压缩包(离线安装)。
4. 校验 SHA256SUMS,再解压到临时目录,逐个对 manifest.files。
5. 先检查冲突:发现 OpenClash、PassWall 等其它代理服务在运行,提示并退出(用 --force 才继续)。名单与 internal/system/conflicts.go 的 KnownConflicts 保持一致。
6. 放文件、写服务脚本、enable、start 后端。只启动后端,不启动 sing-box、不接管 DNS、不改防火墙:这些都要用户在面板里点了才发生。
7. 幂等:重复运行是升级式覆盖二进制和前端,绝不动数据目录和配置目录。

uninstall.sh:
1. 先让后端自己撤销系统改动:调用 openbox-backend cleanup(新子命令,见第十一节 M6-2),它撤销 DNS 接管、拆虚拟终端、停 sing-box,
   并确认完成;cleanup 失败就停下来报错,不继续删除(DNS 还指着一个即将不存在的服务会断网)。
2. 停止并禁用两个服务,删二进制、前端、规则库、服务脚本。
3. 默认保留数据目录和配置目录(重装可恢复);--purge 才删。

两个脚本都要有「假根目录」测试:沙箱里用 dash / busybox sh 加假的 uname、假的下载、假的服务管理器,断言放了哪些文件、顺序、失败时不留半成品。
这部分不需要真机,真实设备上的 procd / systemd 行为由维护者验证。

## 六、构建流水线(草案,手动触发)

文件放 backend/packaging/workflows/release-backend.yml(不直接放 .github/workflows,理由见第十二节第 1 条),
workflow_dispatch,输入:version(发布版本号,如 v0.1.400-main.1)、upstream(上游号)。不在 push 时触发,避免 main 上误发布。

步骤:
1. test:gofmt、go vet、go test -race,装固定版本的 sing-box 跑集成测试(沿用已删除的 backend.yml 的做法)。
2. panel:在 panel/ 里 pnpm install --frozen-lockfile、构建,产出 panel/dist(与架构无关,只做一次,上传为中间产物)。
3. 对 amd64 和 arm64 分别:
   a. go build 后端:CGO_ENABLED=0、-trimpath、-ldflags "-s -w -X main.version=<版本> -X main.builtAt=<时间>"。
   b. build-core.sh 编 openbox-core(不注入 buildID)。
   c. 取 sing-box:SagerNet 官方发布的 sing-box-<版本>-linux-<架构>.tar.gz,版本固定在 backend/packaging/versions.env(现为 1.14.4),
      同一个文件里写每个架构压缩包的 SHA256,下载后必须对得上,对不上就失败。arm64 的文件名按官方发布页核对,首次构建时确认。
   d. 规则库:从固定来源取 geosite-*.srs、geoip-*.srs。草案来源是 SagerNet 公开的 sing-geosite、sing-geoip 的 rule-set 分支,
      在 versions.env 里固定到某个提交,并列出要带的分类清单(现有 geosite-cn、geoip-cn,以及前端默认分流、客户端默认地区用到的)。
      数据来源的许可要维护者核对,见第十二节第 4 条。
   e. 生成 manifest.json、geodata.json,打压缩包。
4. 汇总:生成 SHA256SUMS,建草稿发布(draft),上传压缩包、SHA256SUMS、install.sh、uninstall.sh。
   维护者在 GitHub 页面检查后手动点发布。草稿对 check 不可见(check 已跳过草稿),所以没发布前用户不会被推送升级。
   workflow 要 contents: write 权限,只给这一个任务。

## 七、在线升级(update/run)的流程

前端规格:POST /update/run 带 channel(auto / direct / mirror),进度靠轮询 GET /update/status 的 status 字段
(stage、bytes、total、message、running)和 logTail;阶段名 starting、probing、downloading、verifying、extracting、committing、
restarting_core、done、failed、cancelled;取消只在 committing 之前有效。

互斥:同一时刻只一个升级;和部署、恢复出厂互斥(复用 Deployer.Exclusive 那一套),冲突回 409。

阶段:
1. starting:占位,检查磁盘空间(见下),记日志。
2. probing:按通道探最新版和安装包地址(沿用 check 的逻辑);只认带本架构安装包的发布(第一节第 4 条)。
   auto 先直连、失败再走镜像;mirror 请求 <前缀><原地址>。已是最新则直接 done,消息说明没有更新。
3. downloading:流式下载,边下边算 SHA256,边解压到暂存目录,不把整个包放进内存(路由器内存小)。
   暂存目录放在安装目标所在的文件系统上(DataDir 下的 update/<版本>/),这样提交时是同一文件系统内的改名,原子且不占双份空间。
   空间不足(可用空间小于解压后大小加 10 MB 余量)在这之前就失败。
4. verifying:压缩包整体对 SHA256SUMS(SHA256SUMS 和压缩包走同一通道下载);再逐个对 manifest.files,多一个或少一个文件都失败。
5. extracting:冒烟:用暂存目录里的新二进制跑 openbox-backend -version、openbox-core hello、sing-box version,
   再用新 sing-box 对当前已部署的配置跑 sing-box check;任何一个不过就失败,此时系统还一个字节没动。
6. committing(从这里起不能取消):见下面「提交」。
7. restarting_core:重启后端和内核,等健康,见「重启与看门狗」。
8. done / failed / cancelled。

提交(每个目标文件):先把新文件复制到目标同目录的 <名>.new 并 fsync,再把旧文件改名成 <名>.old,最后把 <名>.new 改名成目标。
Linux 上改名覆盖正在运行的二进制是安全的(新 inode)。前端和规则库是目录:新目录先放成 panel.new,旧的改名 panel.old,再换位。
提交前先写日志文件 <DataDir>/update/journal.json:状态(committing / restarting / healthy / rolled-back)、新旧版本、每个文件的 .old 备份路径。
任何一步失败:按日志里已做的反向改名,恢复旧文件,状态记 rolled-back,阶段 failed,message 写原因。
状态目录快照:提交前把 <DataDir>/state 的 .json 文件(体积小)打成 update/state-<旧版本>.tar.gz,回滚时一起恢复,
防止新版本迁移过状态文件后旧版本读不了。cache.db 和规则集缓存不进快照。

重启与看门狗:后端不能指望自己重启自己后还能判断新版本好不好,新二进制可能根本起不来。设计:
1. 提交完成后,旧进程启动一个脱离自己的 sh 看门狗(脚本内嵌在二进制里,setsid,不依赖新文件),然后请服务管理器重启后端服务。
2. 新进程启动后读 journal.json,状态是 restarting 就做自检:/api/health 通、core hello 通、
   升级前 sing-box 在运行的话,经现有的安全部署路径重启 sing-box 并确认健康(失败走现有的配置回滚);全部通过把状态写成 healthy。
3. 看门狗最多等 90 秒(procd 的 respawn 默认重试几次后就放弃,systemd 有 StartLimit,所以不能等太久;具体参数以真机为准):
   journal 变成 healthy 就退出;超时仍不是 healthy,就用 .old 文件和状态快照恢复,重启服务,状态写 rolled-back。
4. 新进程自检失败时自己也可以立刻写 failed 并退出,让看门狗尽早回滚,不用等满 90 秒。
5. 启动时如果日志停在 committing(提交中崩溃),先按日志回滚再正常启动。

重要:升级不会碰 DNS 接管、防火墙和 sing-box 的配置文件。内核换了新二进制后用现有配置重启,健康检查沿用部署那一套。

取消:在 committing 之前,清理暂存目录,阶段写 cancelled。之后回 409 并说明已经不能取消。
自动升级(profile.updates.openbox 的 auto / hour / days / channel):按路由器时区,到点先 probing,有新版才升级,一天最多一次;
同一个版本失败过一次就不再自动重试(记在数据目录,用户手动点了才重试),避免循环。钟点要按系统时区算(STATUS 时区条目的提示)。

## 八、通道与镜像

channel:auto 先直连、失败再试镜像(镜像前缀来自 -update-mirror / OPENBOX_UPDATE_MIRROR,后端不内置任何镜像地址);
direct 只直连;mirror 只走镜像。下载地址取发布 API 返回的资产下载地址,镜像则前面加前缀。
已知限制:走镜像时,压缩包和 SHA256SUMS 都经过镜像,镜像若恶意可以同时改两个。v1 接受这个限制(与 DESIGN 的「v1 只做 SHA256」一致),
更强的保证要靠签名,须维护者生成密钥放进 Actions secrets。草案在 manifest 里预留 signature 字段,v1 不填、不校验。

## 九、版本号与检查

版本号 v0.1.<上游号>-main.<n>(过渡期,正式发布前由维护者重定)。internal/update 的比较规则不改:上游号相同时带 -main 的更大。
check 改为只考虑「有本架构安装包资产」的发布(资产名 openbox-<版本>-linux-<架构>.tar.gz)。notes 不受影响。

## 十、验证方式

不需要真机的部分(沙箱里做):manifest 解析与校验、流式下载加哈希、解压路径安全(拒绝 .. 和绝对路径、拒绝符号链接逃逸)、
提交与回滚(假文件系统故障注入:每一步失败都回到原样)、日志恢复、看门狗脚本(假服务管理器)、install / uninstall 脚本(假根目录)、
check 的资产筛选、自动升级的调度与失败不重试。
需要真机的部分(维护者做,STATUS 里标 [~],日志写清楚怎么判断成功):procd / systemd 下真的重启并自检、看门狗在故意放一个坏二进制时确实回滚、
OpenWrt 数据目录持久、install 在干净的 OpenWrt 和 Debian 上一条命令装完、uninstall 后 DNS 和防火墙恢复原样。
